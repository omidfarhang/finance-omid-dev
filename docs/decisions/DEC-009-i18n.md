# DEC-009: UI internationalization (English + Farsi)

- **Status:** Accepted
- **Date:** 2026-10-30

## Context

The product targets Iranian personal use first (Persian dates, Iranian bank imports) while remaining usable in English. Profile already stores optional `locale` / `timeZone` hooks ([DEC-007](DEC-007-auth.md)). Design called for RTL-ready Persian support. We need a multilanguage UI that starts with Farsi and English and can grow without a per-locale rebuild pipeline.

## Options considered

- Angular compile-time `@angular/localize` (separate builds / deploy artifacts per locale).
- Runtime libraries (`@jsverse/transloco`, `@ngx-translate/core`) with JSON message catalogs.
- Hand-rolled dictionary service without a library.

## Decision

- Use **runtime** UI i18n with **`@jsverse/transloco`** and JSON catalogs under `apps/web/public/i18n/`.
- Ship **`fa`** and **`en`** first (BCP-47 language tags). Default preference order: `localStorage` → logged-in profile `locale` language subtag → browser language (`fa*` → `fa`) → fallback **`fa`**.
- Set `document.documentElement.lang` and `dir` (`rtl` for Farsi, `ltr` otherwise) when the active language changes; keep layouts RTL-safe with logical CSS where direction matters.
- Persist the UI language in `localStorage` and, when authenticated, in profile `locale` via the existing profile API.
- Wire PrimeNG component locale strings to the active UI language.
- **UI chrome and page copy only** in this decision. API error bodies are not translated server-side; client fallback strings may be translated. Persian (Jalali) calendar formatting remains a separate later concern.

### Adding a language later

1. Add `apps/web/public/i18n/<code>.json`.
2. Register `<code>` in Transloco `availableLangs` and the web `LocaleService` metadata (`label`, `dir`).
3. Optionally add a PrimeNG translation map for that language.

## Consequences

- One SPA build serves all UI languages; users can switch at runtime.
- New languages are mostly translation-file work plus a small registry update.
- Contributors must not hardcode user-visible English in new UI without keys.
- Server message localization would need a separate decision if required.

## Revisit when

SEO/marketing needs locale-specific URLs or builds; or API responses must be localized for non-browser clients.
